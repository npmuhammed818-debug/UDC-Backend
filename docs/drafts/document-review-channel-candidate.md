# Local candidate - not deployed

Branch staging/document-review-portable-chat, based on staging54011b0. No hosted SQL, sends, spending, production or public-site changes. Not a finished customer flow.

## Document review
Staging-only Express route factory. Authenticated self-issue links; recipient-only verification landing page reveals no title/content. User explicitly starts a six-digit WhatsApp verification code. Two-minute browser+link bound challenge, max5wrong codes, single-use atomic consume. Persistent hashed browser session lasts up to7days without sliding extension; every document read still checks account verification, membership, explicit grant, approved document status and version. Cookies HttpOnly/SameSiteStrict/Secure on deployed runtime. Origin enforced on every POST. GET never approves. Receipt means reviewed-only, not acceptance, signature, authenticity verification, bank approval or payment instruction. Seven-day expiry is a local implementation default, not a permanent product policy.

Code persistence uses existing audit table. Atomic budget intended:3requests per recipient/hour,10perIP/hour,60seconds between recipient requests. Recipient never supplied by browser form. Codes hashed with secret+randomchallenge, no plaintext persistence. No live WhatsApp delivery adapter connected: route returns unavailable with no claimed send. No blind retries. A real delivery adapter requires approved sending scope, an appropriate provider authentication template/current window, cost check and final origin/secret configuration. No environment changed.

Storage reads now enforce a20MBlimit during streaming and reject oversized declared bodies before buffering. Receipt transaction locks document, user, deal and grant rows while checking authorization; immutable storage objects are still an operational requirement, not proven here. Consent revoke/role suspension remains enforced on future reads. Existing device/downloaded copies cannot be recalled.

## Channel separation
Transport-neutral contract tests show separately verified adapters can resolve to the same internal user, provider message dedup stays channel-namespaced, and inbound names cannot assert identity. New staging+explicit-flag account-history seam is wired into the real WhatsApp guidance notebook. Default remains the old phone-keyed behavior. In opt-in staging mode verified provider phone lookup resolves existing internal user and derives a channel-neutral account key. Language reads use the same key. Old phone history is preserved, NOT copied into an account key because old rows do not prove original account ownership. Flag has not been enabled.

No Telegram integration or cross-channel binding store/UI. No account merges. Broader trade/profile/session handlers remain WhatsApp-coupled; document-list state still uses its legacy phone key. Memory/deal history already uses internal account IDs. This is partial identity/history isolation, not complete channel portability. Must prove account-history rollout before enabling, and extract remaining transport-specific handlers behind a shared conversation service before Telegram.
